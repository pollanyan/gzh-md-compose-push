# 用户排版特殊约定（必须遵守，逐条取证自 2026-11-24 成品 build_gzh.py）

这些是用户在多轮返工后定下的偏好，**不是可选项**。生成 HTML 时直接照此实现，不要每次重新问。

## 1. 超链接处理

- **公众号正文不插任何超链接**（`<a>` 一律 0）。用户明确要求「正文无超链接，取证来源改引用方式」。
- 来源 URL 只出现在文末 **References 小节**，且是**纯文本**（等宽字体、无底色、可复制但不可点）。
- 正文对应处插引用角标 `[[1]]` / `[[2]]` / `[[3]]`（写在 Markdown 正文里，转换器渲染）。

## 2. 引用角标：数字在右上角

- 格式：蓝色 `#2563EB` + `font-size:10px;vertical-align:super` 上标，如正文 `omp 仓库[[1]]` 渲染成「omp 仓库」后跟蓝色右上角 [1]。
- 取证来源大章节的要点列表：**蓝色来源名 + 蓝色上标角标**（不是普通方括号在基线）。
- 实现见 `md_to_gzh.py: ref_sup()`。

## 3. 三层对照（能力矩阵）

- 用一个**章节内的对照图 + 状态表**表达「三层视角」：图放章节内（浅色细线框、无底色，`<img max-width:100%>`），图下有一行左对齐说明文字。
- 状态列用 **强 / 平 / 弱** 三值并加粗：
  - 强＝已覆盖或更优；平＝主体可用但有边界差异；弱＝未覆盖或不可插件化。
  - 表格 `status_col` 指定该列加粗（实现见 `md_to_gzh.py: data_table(status_col=...)`）。
- 配一行状态说明文字，别让读者猜。

## 4. 表格：列宽按内容适配，不无脑加宽

- 外层 `overflow-x:auto`，table `table-layout:fixed` + `min-width`（约 620–650px），手机横滑不压竖条。
- 用 `<colgroup>` 按内容比例分配列宽：`col_widths` 缺省时由
  `auto_col_widths()` 自动计算（0.55×列最大宽 + 0.45×列平均宽加权，
  不可断片段如 `@narumitw/pi-goal` + 内边距作保底，夹在 8%–60%）；
  显式传 `col_widths` 可覆盖。**禁止无 colgroup 的平均分列**。
- **不要**把所有列都拉宽到 900/1100/1280px——用户明确批评过「无脑增宽」，电脑端要按内容可读。
- 单元格**全边框**（`border:1px solid 线色`，含竖线网格，border-collapse:collapse）；
  表头**居中对齐**、加粗、下边框主题色 2px；正文单元格左对齐。
  （2026-11-25 用户定稿：旧「表头左对齐、只有横线」口径作废。）

## 5. 取证来源章节结构（两轮返工后的定稿）

```
## 附：取证来源            ← 用大章节组件（44px 编号「附」+ 英文 APPENDIX + 中文标题），与 01–05 章同款
• omp 仓库[1]              ← 蓝色来源名 + 蓝色右上标，无超链接
• 工具规范清单[2]
• browser-loop[3]

### References             ← h3 小节
[1] omp 仓库:              ← 等宽、无底色、纯文本
https://github.com/...
```

- 标题必须是「附：取证来源」大章节，不是 `References` 大章、也不是「附：取证来源 References」混合标题。
- References 里每条是 `[N] 标题:` 换行纯文本 URL。
- 正文字号/行距/左对齐与其他部分一致。

## 6. 其它版式偏好

- **全文字左对齐**（去 justify/center，仅 END 装饰线可居中）。
- **正文文字零背景色**（引用/金句/提示用无底色左竖条；代码块用浅色细线框；表头不用深炭实底）。
- **行内代码 `yield`/`goal`/`think`/`resolve` 等用蓝色 `#2563EB` 前景、无底色**（用户指定）。
- 正文每段主动挑 1–3 个核心短语加下划线标记（主题色），即使原文没加粗也要标。
- 章节编号 44px 大号 + 英文标签（CHAPTER/MATRIX/APPENDIX…），严格按 `##` 顺序。

## 7. 代码高亮（2026-11-24 踩坑修正）

- **颜色**：关键字紫 `#7C3AED`、字符串绿 `#15803D`、常量蓝 `#2563EB`、数字橙 `#C2410C`、标点灰 `#71717A`。
- **绝不搞成图片**（用户原话「千万不要搞成图片，因噎废食」）。
- **每行一个 `<span leaf="">`，行内用不带 leaf 的彩色 span**：
  - 早期实现逐 token 一个 leaf，公众号编辑器把每个 leaf 当原子节点重排 → `export const X = [` 被拆成 5 行、缩进错位、行距撑大（用户截图反馈）。
  - 修正后颜色保留、缩进整齐。缩进用 `&nbsp;` 放在 leaf 内，字体 Courier New，`line-height:1.6`。
- 不用 class、不用 `white-space:pre`、不用图片。

## 8. 签名区

- 不要写死任何人名；用 `{{作者名}}` / `{{简介}}` 占位（或用户给了署名就直接填）。
- 有且仅有末尾一处；原文末尾已有署名段就并入，不要重复生成。

## 9. 深浅自适配与深色配色方案（2026-11-25 三次定稿，以微信官方文档为准）

**真实机制**：读者端微信客户端内置官方开源算法 `wechatjs/mp-darkmode`，逐元素读计算
样式并转换颜色——白底→`#1A1A1A`、纯黑字→≈`#A3A3A6`、色相保留、高饱和（饱和度>15）
边框按背景规则保护；仅在深色下「看不清（感知亮度差<65）或刺眼（背景亮度>190/近白）」
才动。**作者按最佳实践写浅色 HEX 内联样式即可自动适配，无需自写深色版。**

- **教训**（2026-11-25）：曾误判「内联样式不会被转换」而连做两版错误方案
  （`color:inherit` 自适配 + 第 7 套 adaptive 主题）。事实：`inherit`/`currentColor`/
  `transparent` 等**关键字**确实不参与转换、且继承色跟随落点容器（编辑器里就会白字），
  但 **HEX 内联样式会被算法正常转换**。判断平台能力必须先查官方文档，不许凭推断下结论。
- 主题颜色规范（= 官方最佳实践）：HEX 格式（颜色名称 black/white 不参与转换）；
  对比度适中；不用文字背景渐变；背景写在容器上；不用 `!important`。
- 深色预览：`scripts/wechat_dark.py` 是官方算法的静态移植（阈值与官方一致）。
  `wrap_preview.py` 生成的每个预览页**自带深浅自适应**——算法转换结果编译成
  `@media (prefers-color-scheme: dark)` + `[style="原始值"]` 属性选择器 +
  `!important` 的 CSS 覆盖规则（样式表 !important 优先级高于内联样式），
  跟随浏览器/系统明暗自动切换，工具栏 🌗 按钮可手动切换（自动/深/浅）；
  `--dark` 表示生成时初始即深色档。DOM 内联样式原样保留，复制出去的仍是
  浅色样式（由微信读者端转换）。
- `--scheme dark`（焊死深色卡片）保留为可选：`DARK_SCHEMES` 每主题一份深底浅字，
  代码块深底 `#101014` + 亮色高亮，行内代码/角标蓝 `#5C9DFF`；适合确定读者
  偏好深色的场景。
- 回归红线：浅色方案输出与历史成品逐字节一致（根背景保持写死 `#FFFFFF`）。
